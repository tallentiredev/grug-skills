# Grug Skill Bridge

Not all skills grug brained. Some skills are big brain — many features, many options, much ceremony. That's ok. Big brain have big brain. Need only be harnessed for good and not in service of complexity demon on accident.

This skill tells grug how to work with non-grug skills without letting demon in.

## Before Calling a Skill

**Say what grug actually needs.** Non-grug skills offer many options. Grug picks the minimum. Don't use features because they exist.

**Scope first.** One sentence: what is this thing for and who uses it? If grug can't write that sentence, grug not ready.

## During

**Let the skill do its job.** It knows its domain. Grug does not fight skill conventions — same rule as tools.

**Watch for demon.** More files than asked for. Abstractions with no second user. Configuration nobody will change. Code grug cannot follow top to bottom.

## After

**Grug review applies.** Regardless of which skill produced it: can grug understand it without jumping between files? Are there good names? Logging? Anything grug would struggle to debug at 2am?

**Simplify, don't discard.** If output is good but complex, trim. Remove what's not needed, keep what earns its place. Don't throw away the skill's expertise — just the demon it accidentally invited.

## Common Bridges

**frontend-design:** Let it pick bold aesthetics — that's its strength. But one file, scoped styles, cut animations that don't serve the user.

**docx/xlsx/pdf:** Let the skill handle format ceremony. Keep content flat, minimal nesting, no formatting for formatting's sake.

**Any code-generating skill:** Output must pass grug-code-style. Intermediate variables, flat, concrete, logged.

## The Rule

Use the skill's brain. Apply grug's taste. Ship something simple that works.
